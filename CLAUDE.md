# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A "Self-Evolving Teaching System" (沉浸式AI智能伴学系统) — a research-grade AI teaching-loop platform. Default course scenario is a university undergraduate *Database Principles* (《数据库原理》) course. The system pairs a Go backend (the "teaching service layer") with a Next.js teacher/admin/student web app. An external LLM gateway ("云雀 / Yunque", spoken to via an OpenAI-compatible `/v1/chat/completions` endpoint) supplies raw LLM capability — its source is *not* part of this repo and must not be modified.

Note: most product copy, comments, prompts, and docs are in Chinese. Match that when editing user-facing strings.

## Common commands

Run from the paths shown; the shell is PowerShell on Windows.

**Backend** (`cd backend`):
```powershell
go run .\cmd\edu-server        # dev server on :18080
go build -o bin\edu-server.exe .\cmd\edu-server
go test .\internal\edu_service\...            # all tests
go test .\internal\edu_service\ -run TestName # single test
go vet .\...
```
There are two binaries under `cmd/`: `edu-server` (the API) and `edu-export-sql` (JSON→Postgres SQL exporter). Tests live in `internal/edu_service/` (`access_test.go`, `sqlite_store_test.go`) and use a separate `study.test.db` — they do not touch dev data.

**Web** (`cd teacher-web-next`):
```powershell
npm install
npm run dev      # Next on http://localhost:3000 (use -p 3001 if busy)
npm run build    # static export → out/ (also used by desktop packaging)
```

**Desktop package** (embeds Next static export into Go binary):
```powershell
.\scripts\build-desktop.ps1
```

**End-to-end smoke test** (backend must be running):
```powershell
.\scripts\smoke-test.ps1       # drives login → CRUD → full teaching workflow against :18080
```

**Reset seed data** to the clean university-course state:
```powershell
.\scripts\reset-university-seed.ps1
```

**Docker** (full stack): `docker compose up -d --build` → backend :18080, web :18081.

## Backend architecture

The whole backend is one package: `internal/edu_service`. `cmd/edu-server/main.go` wires it up and applies CORS + optional bearer-token middleware. Desktop builds embed `cmd/edu-server/web/` (Next static export) via `//go:embed`.

- **`Service`** (`service.go`) is the core. It holds three collaborators behind interfaces:
  - `MemoryStore` — per-student cognitive memory (trust score, weaknesses, thinking style), one JSON file per student in `backend/data/`.
  - `PlatformDataStore` — all structured platform data (schools, users, classes, courses, lessons, homework, sessions, audit). Two implementations selected by `EDU_STORAGE_DRIVER`: `json` (`platform_store.go`) or `sqlite` (`sqlite_store.go`, **default**). The SQLite store keeps the *entire* platform state as one JSON blob in a single `platform_state` row — it is a persistence swap, not a normalized schema. On first run it seeds from `seedState()` (or an existing `data/platform_state.json`); legacy states are auto-migrated by `ensureStateDefaults()` (e.g. backfills the default school and `school_id` on classes/users).
  - `AgentClient` — the LLM gateway (`yunque_client.go`, `YunqueClient`). Runtime-configurable via the admin LLM-config panel (`/系统配置`).
- **`handlers.go`** registers all routes on a stdlib `http.ServeMux` using Go 1.22+ method+path patterns (`"POST /edu/lessons"`, `"GET /edu/students/{id}"`). No web framework. See `README.md` for the full endpoint list; list endpoints accept `page`/`page_size`/`keyword`/`role`/`class_id`/`archived`.
- **Org model**: `School → Class → Course → Lesson/Homework`, plus users with roles. Org admin endpoints: `GET/POST /edu/schools` (admin only); bulk roster import `POST /edu/students/import` (admin+teacher, teacher restricted to own classes). Smart lesson import `POST /edu/lessons/upload` classifies intent (lesson/homework/outline/noise) via `import_classify.go`, skips noise (rosters etc.), and returns a structured import report.

### The teaching loop (the heart of the system)

Four "agents" are just methods on `Service` in `agents.go`, each one system-prompt + LLM call with a deterministic heuristic fallback if the LLM is disabled/unreachable:
- **TeacherAgent** (`teacherAgent`) — parses lesson content into concepts / difficulties / learning path (`KnowledgeAnalysis`).
- **TutorAgent** (`tutorAgent`) — the metacognitive coach. **Never answers directly; only asks guiding questions.** `enforceQuestionOnly()` guarantees output ends in a question.
- **EvaluatorAgent** (`evaluatorAgent`) — scores a student answer (understanding, reflection, error types).
- **ReflectorAgent** (`reflectorAgent`) — aggregates class/student data into common problems + teaching suggestions.

`Service.Workflow` chains Analyze → Chat(tutor) → Evaluate → Report and records a `LearningSession`. Prompts live in `prompts.go`.

**Screen-aware coaching**: `ChatRequest.page_context` (frontend-injected from the homework stage / free-chat scenes) lets the tutor "see" the current step title, instruction, expected hint (never leaked verbatim), and the student's live draft — Chrome-Gemini-style side-panel behavior, but scoped to the learning workspace (no web crawling). RAG queries are enriched with step title/instruction.

**Trust-gated disclosure** (`trust.go`) is the central mechanism: each student has a `TrustScore` (0–100) computed from answer quality. `TrustPolicyFor(score)` maps it to a permission tier — `locked` (question_only) → `hint` → `partial` → `explain`. The tutor's willingness to reveal information is gated by this tier, so a student must demonstrate understanding to unlock more help. When editing tutoring behavior, respect these tiers.

### Access control

Roles are `admin`, `teacher`, `student`. Every `Service` method that mutates or reads scoped data calls `RequireRole(ctx, ...)` and the `requireXAccess` helpers (`access.go`); `DashboardFor` filters the dashboard by role (teachers/students only see their own classes — and, for schools, only schools containing their visible classes). Org endpoints (`/edu/schools`) are admin-only; `/edu/students/import` allows teachers but enforces class ownership. Conversations are per-user. The authenticated user is injected into the request context by `AuthMiddleware`. When adding an endpoint, follow this pattern — do not read platform data without a role/access check.

### Data-flow invariants to preserve

- **LLM-optional**: every agent has a heuristic fallback and the code checks `LLMConfig.Enabled`. New agent logic should degrade gracefully when the LLM is off, not error.
- **RAG**: lesson retrieval (`retrieval.go`) is a keyword-scoring search over lessons in platform state, scoped by course — there is no vector DB.
- **Sanitization**: user/LLM-config responses pass through `sanitize.go` (`sanitizeUser`, `sanitizeLLMConfig`) to strip password hashes / API keys before serialization. Keep new response paths sanitized.

## Frontend architecture

`teacher-web-next` is a Next.js App Router SPA (static export for desktop/Docker).

- Real routes: `/login`, `/admin`, `/teacher`, `/student` with `RoleGuard` in each layout.
- Global state + API actions: `components/session-provider.tsx`.
- Admin/teacher UX is chat-first (`components/portal/chat-shell.tsx` + slash commands in `lib/commands.ts`). LLM config opens via `/系统配置` → panel `llm-config`.
- Student portal: mobile-oriented scenes under `components/portal/student-*.tsx`.
- API base: `NEXT_PUBLIC_API_BASE_URL` (dev default `http://127.0.0.1:18080`; desktop build uses `same-origin`).
- Types: `lib/types.ts`; API client: `lib/api.ts`.

## Storage note

SQLite is the recommended/default driver. Postgres schema (`backend/migrations/`), `docker-compose.postgres.yml`, and the `edu-export-sql` tool exist only as a future large-scale migration path — the app does not run against Postgres today. See `docs/SQLITE_DEPLOYMENT.md`, `docs/POSTGRES_MIGRATION.md`, `docs/DEPLOYMENT.md`.
